## 1. Your job

Test the whole product as it stands on GitHub `main` (commit `abef9da` or later). You have two goals:

1. **Find** every serious problem that can be found, using methods that do not depend on anyone guessing where bugs are.
2. **Fix** them at the root, so that each kind of bug cannot come back, and prove that nothing else changed.

You are not here to confirm earlier work or to raise a score. A low score that anyone can reproduce is a good result. A high score that nobody can reproduce is a failure. Every claim in your final report must point to a file, a command or a test that another person can run again.

The product is District IQ, the entry for FarmwiseAI Campus Product Challenge Task 6: a Collector's platform for Chennai with citizen, officer and Collector portals, the Jarvis voice assistant, Ask District IQ, a live map, briefings, trends and Data Studio.

**Scale:** the owner asked for the largest scale. There is no limit on agents or time, so use 100 or more agents if the work benefits. Run independent work in parallel. Make your own decisions and keep going. Do not stop to ask. The only things held back for the owner are in section 4.

**Independence:** the authors of the test sets, the bug hunters, the fixers, the reviewers, the skeptics, the judges and the final auditor each start fresh and never see each other's conclusions. Treat what any agent reports as a claim until it is verified.

Traps:
- **Startup replaces the local store.** The first query after a server starts downloads a fresh read-only copy and overwrites the durable file. Test accounts vanish. Write `tests/qa/seed-local-users.mjs`, which adds a Collector, officers in two departments and a citizen directly to the local file with bcrypt hashes, and run it after each store load. In dry-run these rows never reach AWS (`store.ts` line 378).
- **The snapshot and the clock move.** Each start can load a newer build, and "today" follows the clock. Log the build id (`[aws-store] ... applied to build ...`) and compare figures only within one build. For the golden master, pin one snapshot and freeze the clock in the test harness, without changing production behaviour.
- **Builds edit config.** `npm run build` with a custom `NEXT_DIST_DIR` changes `tsconfig.json`. Restore it after each build.
- **A running server writes files and spends quota.** It saves to `data/i18n/*.json`, and its background jobs call Groq. Never commit those files.
- **Harness gaps.** `src/lib/thunai/qa.live.ts` uses fake hands, so it measures wording and not the data. `QA_LIVE=rules` leaves out the resolver; `rules2` includes it. Build your scoring on `serverWorld()` and `serverHands()` through `planRound`.
- **Mutation runs change source.** Never run them during a build or a fix, and always restore afterwards, or run them on a copy.
- **The browser pane blocks the microphone and has a fixed size.** Use Playwright for Edge, other viewports and fake audio.
- **The old 180-row set is no longer blind.** Use it only as a regression set, and say so.

### Phase 2: Content grader, oracle and data truth

Write a grader that checks each answer against the real store, with three outcomes: **right**, **safe** (asked back, handed off, or said it has no data) and **wrong**. It checks the following:
- A retold case matches the topic and place asked.
- Every row of a list matches every filter.
- Every spoken figure equals the oracle.
- Open and closed are told correctly.
- The reply is in the language asked.

Report confident wrong answers first, because they matter most. Then extend the oracle:
- **Same number everywhere.** Compare the console, briefing, trends, officer pages, Ask District IQ and Jarvis for the same scope, and reconcile differences row by row. Last time, 237 against 240 and 12 against 13 were explained but never reconciled.
- **Decision matrix.** Apply resolve, reject, reopen, verify, escalate, note and an officer's close on a throwaway copy, and record what moves on every surface. Include the known gaps: `assistant/compile.ts` and `assistant/lance.ts` (OPEN-16).
- **Data invariants.** Write SQL checks over the real snapshot: closed after opened, flags that agree with status, wards inside their zones, valid departments and categories, duplicates, impossible dates, and totals that add up across tables.

### Phase 3: Audit of the 37 fixed bugs

### Phase 4: The test factory

These methods find bugs nobody thought to look for. Save each as a permanent test where it runs fast enough.
- **Mutation testing:** run Stryker with the Vitest runner on the critical modules. For every surviving mutant, add a test that kills it, or justify it as equivalent.
- **Property-based testing (fast-check):**
  - Redaction: any phone, Aadhaar or email in any format is hidden, and ordinary text is left unchanged.
  - The number gate: a figure not in the data never passes.
  - The resolver: it never throws, stays within its time limit, and any other place plus any body word never matches ours.
  - `effectiveStatus` and its SQL version agree.
  - Week and month keys hold in every time zone, CSV cells are safe from formula injection, and rate limits hold.
- **Metamorphic testing:** the facts must stay identical across language, filler words, word order, plurals, Tamil case endings, spelled-out numbers and polite forms.
- **Word pattern audit:** list every regex, keyword list and `includes` matcher in `src/lib/thunai` and `src/lib/assistant`. Run them over every real title, category and place, and over an adversarial corpus. Report each case where a word matched inside another word, or where a broad word beat a specific one.
- **Unicode fuzzing:** NFC and NFD Tamil, zero-width characters, mixed scripts, Tamil digits, emoji, very long input, and right-to-left marks, on every text input.
- **API fuzzing:** generate malformed requests for all 116 routes from their schemas (wrong types, missing fields, huge bodies, null bytes). No 5xx, no stack trace, no partial write.
- **Access matrix:** generated from the route files, all 116 routes against anonymous, citizen, officer A, officer B and Collector, checking both status and data scope.
- **Model-based testing:** run long random action sequences against a model of the complaint lifecycle, the officer workflow, sign-in with per-tab sessions, and a Jarvis conversation (follow-ups, ordinals, corrections, barge-in state, tray), checking invariants after each step. Shrink failures to the shortest sequence.
- **Concurrency:** double submits, two tabs, two officers on one case, a decision arriving during a read, a stop during a slow answer. Check for lost updates and mixed-up answers.
- **Time travel:** with a fake clock, cross IST midnight, Mondays, month and year ends, Pongal, the daylight difference between UTC and IST, and empty periods, on every period-based figure.
- **Combinations:** pairwise coverage of zone, department, taluk, category, severity, status and period across the console, map and exports, with the oracle checking each result.

### Phase 7: The fix engine

**Scope:** every P0 and P1, and every P2 and P3 where the fix is safe, including the open items that are not the owner's or the pipeline's (OPEN-4, 5, 6, 10, 13, 15, 16, 17, 18). Flaky tests are bugs.

**Triage:** put all verified findings in one ledger. Cluster them by root cause, not by symptom. One mechanism behind ten bugs gets one fix. Rank by harm and likelihood. Use `git log` or `git bisect` to find the commit that introduced each serious one.

**For each cluster,** a fresh fixer agent, working on files no other fixer is touching:
1. Writes a failing test first.
2. Writes down the root cause and why earlier tests missed it.
3. Fixes the mechanism, not the sentence that exposed it. Adding one phrase to a list is not a fix. A list is right only for complete reference data, such as a gazetteer with a stated source.
4. Sweeps for the same class of bug and saves the search output.
5. Adds a **class guard**: a test or lint rule that fails if this kind of bug returns anywhere (for example, no raw `i.is_open` in figures, and no word pattern without boundaries).
6. Checks all three languages, on the real snapshot.
7. Runs the golden-master diff. Every changed output is explained. An unexplained change blocks the fix.
8. Runs the open set before and after, and resolves every right-to-wrong row. Checks that no latency budget got worse.

**Then, without the fixer's explanation:**
- A reviewer agent reads the diff and judges it against the root cause. P0 fixes get two reviewers.
- A skeptic tries to break it.

**Integrate one fix at a time.** After each one, run the type check and the full tests, then commit with the bug ids.

**Repeat hunting with fresh agents after fixing. Stop rule:** two passes in a row find no new P0 or P1, with at most five passes. If the rule is not met, say so plainly and show the discovery rate per pass.

Research open-source methods where they help. Keep going while the open-set score keeps improving and confident wrong answers do not rise. A safe answer is always better than a confident wrong one.

## 7. Severity and "fixed"

- **P0:** a wrong number, a confident answer about the wrong thing, a privacy or security failure, an unsafe action, a crash, data loss, or broken sign-in.
- **P1:** the feature does not do what it says.
- **P2:** works, but confusing, slow or misleading.
- **P3:** polish.

"Fixed" means all of these:
- A test failed before the fix, and reverting the fix makes it fail again.
- The root cause is written down.
- The class sweep is saved and a class guard exists.
- The golden-master diff is explained.
- It was checked on the real path, in a browser or a real run.
- A reviewer read it and a skeptic tried to break it.

Each row says which parts are met. If a part is missing, the row says so and it is not counted as fully fixed.
